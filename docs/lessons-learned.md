# Lessons Learned

## Design the Recursive-Trigger Solution Before Automating Git Commits

One of the most important lessons from this project was recognizing that automated version commits create a natural feedback loop when the repository is connected to a webhook-triggered Multibranch Pipeline.

The sequence is straightforward:

```text
Pipeline runs
    ↓
Version is incremented
    ↓
Jenkins commits the new version
    ↓
GitHub receives a new commit
    ↓
GitHub sends a webhook
    ↓
Jenkins starts another build
```

Without protection, Jenkins could repeatedly trigger itself.

The solution was to deliberately design the recursive-trigger mechanism as part of the pipeline architecture rather than treating it as an unexpected failure.

The Jenkins-generated commit contains:

```text
[jenkins-skip]
```

The next pipeline execution checks the latest commit message. If the marker is present, the pipeline skips the remaining stages.

This reinforced an important engineering principle:

> Automation that changes the system should also account for the events generated by its own changes.

## Credentials Belong in Jenkins, Not in Source Code

This pipeline uses several sensitive credentials:

* Docker Hub credentials
* SSH deployment credentials
* GitHub Personal Access Token

The Jenkinsfile references these credentials by ID:

```text
Docker-Hub-Credentials
deploy-ssh-credentials
GitHub-PAT
```

The actual secret values are stored in Jenkins Credentials rather than committed to Git.

The pipeline retrieves credentials only when they are needed, using Jenkins mechanisms such as:

```groovy
withCredentials(...)
```

and:

```groovy
sshagent(...)
```

This separation makes the Jenkinsfile reusable without exposing authentication material in the repository.

The broader lesson is that **configuration can be version-controlled while secrets should be managed by a dedicated secret/credential system**.

## Same-Host Deployment Is Useful for Learning, but It Is a Trade-Off

The original design goal was to demonstrate Jenkins deploying an application through SSH. During implementation, the deployment target ended up being the **same AWS EC2 instance that hosts Jenkins**.

The final topology is:

```text
AWS EC2
│
├── Jenkins container
│   └── Host port 8080
│
└── Application container
    ├── Host port 8081
    └── Container port 8080
```

This introduced an important practical issue: Jenkins already occupied host port `8080`.

The application therefore had to use:

```bash
-p 8081:8080
```

instead of:

```bash
-p 8080:8080
```

This experience reinforced that architecture decisions affect seemingly simple deployment commands.

It also highlighted the trade-off of same-host deployment:

**Advantages for the learning environment:**

* Less infrastructure to provision.
* Lower cost.
* Easier experimentation.
* Still demonstrates SSH-based deployment.
* Allows the complete CI/CD flow to be tested end-to-end.

**Trade-offs:**

* Jenkins and the application share the same infrastructure boundary.
* A problem with the host can affect both CI and application runtime.
* Resource contention is possible.
* It does not represent a fully separated CI/CD and runtime architecture.

A future version of the project can move the application to a separate EC2 instance or Kubernetes/EKS environment.

## Port Conflicts Are Architecture Problems, Not Just Docker Problems

The deployment initially attempted to use the application's container port directly on the host:

```text
8080:8080
```

However, Jenkins was already using host port `8080`.

The problem was not with the application itself. It was a host-level port allocation conflict.

The final mapping became:

```text
Jenkins
EC2 host :8080
      ↓
Jenkins container :8080

Application
EC2 host :8081
      ↓
Application container :8080
```

This reinforced the importance of distinguishing between:

* host ports
* container ports
* service ports
* externally exposed ports

Understanding that distinction is essential when working with Docker and Kubernetes networking.

## Branch Strategy Should Be Designed Before Writing `when` Conditions

The pipeline deliberately gives different branches different responsibilities.

| Branch      | Test | Version | Build | Docker Image | Push | Deploy |
| ----------- | ---: | ------: | ----: | -----------: | ---: | -----: |
| `feature/*` |    ✓ |       — |     ✓ |            — |    — |      — |
| `develop`   |    ✓ |       ✓ |     ✓ |            ✓ |    ✓ |      — |
| `main`      |    ✓ |       ✓ |     ✓ |            ✓ |    ✓ |      ✓ |

This means experimentation can happen on feature branches without publishing or deploying every change.

`develop` provides an integration path where a versioned Docker image can be built and published.

`main` represents the deployment path.

The lesson was that branch-based CI/CD becomes much easier to reason about when the desired promotion model is defined before implementing the Jenkinsfile.

## Application Versioning Can Become the Source of Truth for Docker Tags

The pipeline reads the application version from `pom.xml`.

For example:

```text
1.1.0
```

is incremented to:

```text
1.1.1
```

The same version is then used for the Docker image:

```text
docker.io/pierrechukason/my-demo-app:1.1.1
```

This creates a useful relationship between:

```text
Git commit
      ↓
pom.xml version
      ↓
Docker image tag
      ↓
deployed application version
```

Instead of relying on ambiguous tags such as:

```text
latest
```

the deployment can identify the application version explicitly.

This makes it easier to understand which application version was built and deployed.

## Jenkins Is More Than a Pipeline Runner

This project changed my understanding of Jenkins from simply being a tool that executes shell commands to being an orchestration layer connecting several systems.

The pipeline coordinates:

```text
GitHub
   ↓
Webhook
   ↓
Jenkins Multibranch Pipeline
   ↓
Maven
   ↓
Docker
   ↓
Docker Hub
   ↓
SSH
   ↓
Deployment host
   ↓
Running application
```

Jenkins is therefore responsible for coordinating the workflow while the individual tools perform specialized tasks.

That distinction helped make the architecture easier to understand.

## Troubleshooting Should Reproduce the Problem Outside Jenkins Where Possible

A useful lesson from the deployment troubleshooting was that not every failure should immediately be debugged inside the Jenkinsfile.

For example, when SSH deployment failed, the underlying SSH connection could be tested independently.

Similarly:

```bash
docker version
```

can verify Docker access.

And:

```bash
curl http://localhost:8081
```

can verify that the deployed application is reachable from the EC2 host.

This creates a useful troubleshooting principle:

```text
Pipeline failure
      ↓
Identify underlying operation
      ↓
Test operation independently
      ↓
Fix infrastructure/configuration
      ↓
Return to Jenkins
```

This is usually faster than repeatedly changing pipeline code when the underlying problem is actually networking, permissions, credentials, or Docker configuration.

## Docker Socket Access Is a Significant Privilege Boundary

Running Jenkins in Docker introduced another important operational lesson.

For Jenkins to build and run Docker images using the host Docker daemon, the Jenkins environment needs access to the Docker socket:

```text
/var/run/docker.sock
```

That access is powerful because control of the Docker daemon can effectively provide significant control over the host.

Therefore, while Docker socket access is convenient for a learning environment, it should be treated as a security-sensitive architecture decision.

Future implementations could explore alternatives such as:

* Docker-in-Docker
* dedicated build agents
* Kubernetes-based Jenkins agents
* cloud-native build services
* isolated container builders

The important lesson is that convenience and privilege should always be considered together.

## CI and Runtime Infrastructure Should Eventually Be Separated

Although this project currently uses the same EC2 instance for Jenkins and application deployment, the architecture provides a useful foundation for evolving toward a more realistic environment.

A future topology could be:

```text
GitHub
   ↓
Jenkins
   ↓
Docker Registry
   ↓
Separate Deployment Host
   ↓
Application
```

Or eventually:

```text
GitHub
   ↓
Jenkins
   ↓
Container Registry
   ↓
Amazon EKS
   ↓
Kubernetes Workloads
```

The current same-host implementation is therefore best viewed as a practical learning architecture rather than the final infrastructure design.

---

## Documentation Should Reflect the System That Actually Exists

Another important lesson was the difference between documenting an intended architecture and documenting an implemented architecture.

Early documentation described a separate deployment server, but the final working environment uses the same EC2 instance for Jenkins and application deployment.

Updating the documentation to reflect that reality is important.

Technical documentation should answer:

> "How does this system actually work right now?"

rather than:

> "How was I originally planning for it to work?"

This makes the repository more trustworthy and makes it easier for another engineer to reproduce the project.

## A Successful Pipeline Is Not the End of the Engineering Work

Getting the complete pipeline to run successfully was an important milestone:

```text
Test
  ↓
Determine Version
  ↓
Increment Version
  ↓
Build
  ↓
Build Docker Image
  ↓
Push Docker Image
  ↓
Deploy
  ↓
Commit Version Change
```

However, the working pipeline also exposed several areas that would need improvement before treating the architecture as production-ready.

Potential next steps include:

* Separate Jenkins and deployment infrastructure.
* Move deployment to Kubernetes/EKS.
* Introduce image vulnerability scanning.
* Add deployment approvals where appropriate.
* Implement rollback strategies.
* Add application health checks.
* Add observability and centralized logging.
* Use AWS Secrets Manager or another dedicated secrets platform where appropriate.
* Improve Docker image hardening.
* Introduce image signing and verification.
* Consider GitOps for Kubernetes deployments.
* Improve versioning beyond the current patch-bump implementation.
* Add automated validation of the Jenkinsfile.
* Introduce reusable Jenkins Shared Libraries as the pipeline grows.

The main lesson is that **"the pipeline works" and "the pipeline is production-ready" are two different engineering milestones.**

---

## Final Engineering Takeaway

This project reinforced that CI/CD is not simply a sequence of commands.

It is a system of interacting components:

```text
Source Control
      +
Branch Strategy
      +
Automation
      +
Credentials
      +
Build System
      +
Containerization
      +
Artifact Registry
      +
Networking
      +
Deployment
      +
Observability
```

The most valuable part of the project was not getting every command to execute successfully. It was learning how failures at one layer can originate from another layer, and how architectural decisions affect the behavior of the entire delivery system.

The project therefore became an exercise in **engineering judgment**, not just Jenkins configuration.
